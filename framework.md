# AI-Assisted Course Project Framework

*A reusable way to give a course project in which students direct an AI harness with internet access, without paid subscriptions, graded by TAs reproducibly and fairly. Written for the professor. Vocabulary is fixed in [CONTEXT.md](./CONTEXT.md); this document uses those terms exactly.*

---

## 1. The design in one paragraph

A project is a professor-controlled **published resource** carrying a **twist** on a well-known problem, plus an **interface contract**, a **public test suite**, and a **hidden test suite** organized in **test categories**. Students may develop with any tool they like, but the grade comes only from what the **reference harness** does with their work. The reference harness is a free, local, pinnable model, so every regeneration is **reproducible** and every student's submission faces identical conditions. Two **project types** share all of this machinery and differ only in the graded object: **Type A** grades the solution the student submits; **Type B** grades the solution the reference harness produces from the student's **specification**. The published resource instructs the harness to sign a **ledger**, which is how "the harness used the internet" becomes a checkable fact rather than a claim.

Everything else in this document is consequences of that paragraph.

## 2. Why not just grade the prompt

The previous version of this project (Spring 2026, `docs/research/prior-project-spring-2026.md`) was a Morris variant on a 23-point board: four parts, eight programs, each submitted as a `prog.prompt` and a `prog.py`, the Python "generated by ChatGPT" through an interactive session that ended with ChatGPT writing the prompt. The grading checks were: the prompt should regenerate a functionally identical program; the program implements the algorithm from class; the output format matches; the program is run and graded on correctness.

That design was already most of this framework. Its first check is a Type B regeneration; its fourth is Type A grading. What it left open is every parameter that decides whether the first check passes:

1. **Which model** regenerates from the prompt. "ChatGPT" spans several models and changes weekly.
2. **Temperature and sampling.** Unspecified, so a regeneration is a draw. This is the "temperature was not accounted for" complaint.
3. **How many attempts.** A prompt that works one time in five is a pass or a fail depending on the grader.
4. **What "functionally identical" means.** Same board and estimate? Same count of positions evaluated? The count depends on move-generation order, which the handout explicitly allows to vary, so two correct programs print different numbers.
5. **"Not allowed to change the code directly."** Unverifiable from the submission.
6. **"Generated by ChatGPT."** Ties the project to one vendor and its paid tiers. This is the "better model access did better" complaint.

All six share a root cause: the thing that produced the graded output was chosen by the student, not the course. The fix is structural, not a rubric change.

**The course owns the execution.** The student owns the specification (Type B) or the solution (Type A); the TAs execute under fixed conditions; the grade comes from that execution and nothing else. Once the course owns the execution, the model is pinned, temperature is a parameter you set, attempts are a policy you choose (§6), "functionally identical" becomes a stated **equivalence policy** per test category (§9), and model access stops mattering because the graded model is the same for everyone.

There is evidence this works at the small-model end. Xavier's own reproducibility harness for that project regenerated all eight programs from rewritten prompts on `gpt-4o-mini` at temperature 0: the first rewrite scored 60/100 on average with four programs failing; after the ten failure patterns were folded into the prompts as explicit constraints, every program scored 100/100 and was deterministic. A specification that a small pinned model can execute is achievable, and writing one is exactly the skill Type B grades.

A colleague will ask: "then why not have the TAs read and grade the prompt directly?" Because grading a prompt on its merits is exactly the subjective judgment that produces inconsistent grades and appeals. A prompt is a program in a language whose interpreter is a model. You grade programs by running them.

## 3. Anatomy of a project

Every project, regardless of type or domain, consists of these parts. The professor authors all of them; the templates in `templates/` and the four worked examples in `examples/` show the shape.

| Part | What it is | Who sees it |
|---|---|---|
| **Published resource** | A page at a URL you control that states the task and the twist, contains the ledger nonce, and instructs the harness to sign the ledger. | Everyone |
| **Twist** | The deliberate deviation from the canonical problem. Lives in the published resource. See the [twist checklist](./templates/twist-checklist.md). | Everyone |
| **Interface contract** | Language, entry point, input/output format. Default: Python 3, `solve.py`, one JSON object on stdin, one on stdout. Alternative, as in the previous project: `python3 prog.py <input file> <output file> <args>` with a fixed stdout format; the test runner supports both. | Everyone |
| **Public test suite** | A small sample of test cases in the contract format, hinting at but not revealing the twist's edge cases. | Everyone |
| **Hidden test suite** | The full suite, organized into named categories with weights. Released after grades are out. | TAs; students after grading |
| **Test categories** | Names and counts of the hidden groups. Students see the names and counts, not the cases. | Everyone |
| **Reference specification** | Your own Type B specification that clears the hidden suite on the reference harness. The calibration gate (§7) and the appeals answer key. | Professor, TAs |
| **Ledger** | Write-only endpoint on your site that appends signed entries to a text file. | Professor, TAs |

The published resource is the only structural lever that forces harness use with internet access. A project with no published resource is a traditional project that permits AI, and the framework says so plainly rather than pretending otherwise.

## 4. The two project types

Both types use the same published resource, twist, contract, tests, and ledger. They differ in what is submitted and what is graded.

### Type A: Mastery Project

*The student's understanding of course content is assured by the difficulty of getting a correct solution, not by TA inspection.*

- **Submitted:** the solution (a directory satisfying the interface contract), a **process note**, a **written component**.
- **Graded:** the solution against the hidden suite, run once (deterministic). The ledger is a **gate**: no signed entry for the student's ID, the submission is incomplete until resolved.
- **Regeneration:** none. This is the type's whole appeal: cheap, deterministic grading.
- **What the harness's internet access proves:** the ledger entry shows the harness fetched and followed the resource. Whether the student also read the page by hand is not graded and the handout says so.

### Type B: Specification Project

*The student's skill at specifying a problem precisely enough that a harness solves it.*

- **Submitted:** the **specification** (a `SPEC.md` of at most 1,500 words, supporting files count toward the cap), a process note, a written component.
- **Graded:** the solution the reference harness produces from the specification, under the **best-of-K** policy (§6), against the hidden suite. The ledger is **informational** (the TA runner did the fetch; the entry confirms the runner worked and that the specification told the harness to sign).
- **The specification carries the sign instruction.** The runner does not inject it. A specification that forgets to tell the harness to sign the ledger has failed to specify the task, and that is graded behavior. The handout states this in one bold line.

### Choosing between them

| Prefer Type A when… | Prefer Type B when… |
|---|---|
| The learning goal is the algorithm or data structure itself | The learning goal is precise specification and verification |
| TA time is the binding constraint | Machine time is available and TA time is not |
| You want deterministic grading and no regeneration policy to explain | You want the model-access problem removed entirely |
| Students are expected to read and own the code | Students are expected to reason about what they told the machine |

Both can run in the same course with the same infrastructure. The graduate section can run Type B while the undergraduate section runs Type A on the same published resource.

### How the previous project maps

The previous project submitted both `prog.prompt` and `prog.py`, which is Type A grading plus a Type B regeneration used as a reproducibility check. The framework does not provide that combination; §15 says what building it would take. Pick the type by what you want to grade: the solution (Type A) or what the reference harness makes of the specification (Type B).

**Multi-part projects.** The previous project had four parts weighted 45/35/10/10. The framework handles this as one project directory per part, each with its own contract, tests and categories, graded separately and combined with `tools/combine_parts.py`. Example 01 shows the shape.

## 5. The reference harness

### The rule

The framework does not name a harness. It names **criteria**, and the professor picks an instance each semester, because free tiers and tools change every few months (see `docs/research/harness-survey-2026-09-08.md` for the survey behind this section).

A reference harness must be:

1. **Free for every student**, with no card and no paid plan, including for practice runs during the project.
2. **Equipped with built-in web fetch**, so the published resource works without extra wiring.
3. **Runnable headless** from a script, so TAs batch it.
4. **Temperature-settable**, so the schedule in §6 is real.
5. **Model-pinnable**, so the semester's model is the same on day 1 and on grading day.

Criterion 1 removes every cloud harness whose free tier can reroute or rotate models mid-semester, and it removes Claude Code entirely (no free path at time of survey). Criterion 5 is what makes appeals possible.

### This year's instance

**OpenCode + Ollama, model `qwen2.5-coder:14b`.**

- OpenCode is the only free open harness surveyed with both web fetch and web search built in, headless JSON output (`opencode run`), and a pinnable `ollama/<tag>` model.
- Ollama gives pinned weights, a `seed` parameter, and a `temperature` parameter. Per-slot model variants are created from a Modelfile so the pin is harness-independent.
- 14B is the smallest model size to trust with following a one-page resource and satisfying an interface contract. It needs about 9 GB of RAM. Masters-level CS students are expected to have that hardware; the computer lab and the SSH server are the fallback, and the runner takes the Ollama server address as a parameter so a shared server and a laptop produce comparable runs.

### Documented alternatives

- **Gemini CLI** (Google sign-in, 1,000 requests/day, built-in search and fetch, headless, temperature settable). The free-cloud choice when a local model is not viable. Its free tier may reroute models, so regenerations are not reproducible; document that in the handout if you pick it.
- **Aider or Goose on Ollama.** Same reproducibility as OpenCode, weaker or absent web tools; require MCP or scraping wiring.

### Students may use anything to develop

The handout says: develop with whatever you like, but the grade comes from the reference harness, so optimizing for a paid tool is pointless. Students install the reference harness by the milestone (§10) and run the same runner script the TAs use, minus the secret seeds.

## 6. Regeneration policy (Type B)

**Best-of-K, K=3, fixed temperature schedule, secret per-slot seeds.**

- Each specification is regenerated three times: at temperatures **0.2, 0.6, 1.0**, in that order, identical for every student. This is the fairness argument in one sentence: every specification faced the same three conditions.
- Each slot has a fixed **seed**, secret until grades are released and published with the hidden tests afterward. Secret because published seeds invite seed-fitting; fixed because a regrade or appeal must rerun bit-for-bit.
- The grade is the hidden-test score of the **best** of the three runs. Best, not median, because the professor chose to give students the best chance; the fixed schedule and seeds keep it fair.
- A run that times out (default 20 minutes wall clock, calibrated to twice what the reference specification needed) or produces a solution that fails to start scores zero for that run. Best-of-K absorbs it.
- "Reproducible" means: same weights, seed, temperature, and wrapper prompt produce the same result unless a tool result or the published resource changed. It does not mean deterministic; an agent loop with web access never is. Freeze the published resource during grading.

**Appeals.** A student who believes a run was unlucky gets one additional regeneration at the middle temperature, granted only if they show the specification passes the public suite on the reference harness. Best-of-K makes this rare.

## 7. Calibration: the one rule you must not skip

**Before the assignment is released, your reference specification must pass every hidden test in at least one of the K regenerations on the reference harness.**

If it cannot, the twist is too hard for the model, not for the students, and the grade would measure model capability rather than student skill. Fix the twist, the resource wording, or the contract until it passes. This costs one afternoon and is the single most important fairness control in the design.

The calibration run also sets the regeneration timeout (twice the reference specification's wall-clock time) and produces the answer key for appeals. The [calibration checklist](./templates/calibration-checklist.md) walks through it.

## 8. The ledger

The published resource contains an instruction like:

> Before writing any code, sign the course ledger: POST to `<ledger-url>` with `student_id=<your ID>` and `nonce=<the nonce printed on this page>`.

The ledger endpoint:

- accepts **one or two student IDs** in the form `XXXNNNNNN` (three letters, six digits), validated by regex; pairs both sign;
- records a **server timestamp**;
- accepts a **run tag** (the runner sets `grading-k1`, `grading-k2`, `grading-k3`; student practice runs carry `practice`), so TA entries are filterable;
- requires the **nonce** printed on the resource page, which turns the entry from "someone hit the endpoint" into "the harness read the page";
- is **write-only**; the file is visible to the professor and TAs. Student IDs are institutional identifiers and do not belong in a public file;
- returns a plain error on malformed input so a harness can self-correct.

The framework ships a reference ledger server (`tools/ledger_server.py`, standard library only) that also serves the published resource. If your site already has a service, port the one route.

The ledger cannot distinguish a harness fetch from a student typing `curl`. Don't try. The resource content is what the task needs; how it was fetched is not graded, and the handout says so under "What is not graded."

## 9. Grading

### Arithmetic

| Component | Weight | How |
|---|---|---|
| Milestone | 10 | Auto pass/fail: public suite passes through the reference harness by the one-third mark |
| Hidden test suite | 70 | Weighted by category; **twist categories carry half of the 70** |
| Written component | 20 | Three dimensions, 0–3 each, one page-limited document |
| Ledger (Type A only) | gate | No signed entry, submission incomplete |

Flat pass rate would let a canonical solution that ignores the resource collect most of the points from the non-twist cases. Weighting the twist categories is what makes reading the resource load-bearing.

The rule precisely: the twist categories' weights sum to exactly half of the non-graduate weights; a part whose categories are all twist categories is allowed and the rule then applies trivially (all of the non-grad weight is twist, so the professor must either add a non-twist category or accept that the part is entirely twist, and say which in the handout). `scripts/review_checks.py` enforces it; an all-twist part passes only when `project.json` declares `"all_twist": true`.

### Equivalence policy

"Functionally identical" is not a test. Every hidden category states what counts as a pass, and the category's `check.py` implements it. The policies the previous project needed, now named:

| Policy | Passes when | Use for |
|---|---|---|
| `strict` | Output equals the expected output exactly | Deterministic, order-independent outputs |
| `estimate` (or "value-only") | The graded value matches; the choice may differ on ties | Search problems where several moves share the best value |
| `ab` (or "same-value-fewer-nodes") | Same value as the reference algorithm, strictly fewer evaluations | Pruning versus exhaustive search |
| `valid` | The output is a legal solution of the stated cost, checked constructively | Path-finding, scheduling, anything with multiple optima |

An output that depends on iteration order (a node count, a visit order) is either removed from the graded output or the contract fixes the order. Grading it against one reference without fixing the order fails correct work; the twist checklist now says so.

### Written component

One page-limited document, one rubric, under ten minutes to grade. See [rubric](./templates/rubric.md).

| Dimension | 0–3 | Type A prompt | Type B prompt |
|---|---|---|---|
| Accuracy | Does the explanation match what the code / specification actually does? | Explain one design decision in the solution. | Explain how you developed the specification. |
| Twist specificity | Does it name what handles the twist and why? | Which part of your solution handles the twist? | Which lines of your specification handle the twist? |
| Candor | Does it identify a real limitation or failure? | Name one input class your solution handles badly. | Name one thing the harness got wrong and what you changed. |

Candor is what makes a page hard to fake with a model.

### Graduate bar

Same project, no extra TA load:

- one **extra hidden test category** only graduate submissions are run against (a harder twist variant or a performance bound), added to the same arithmetic so the graduate denominator is larger;
- one extra written dimension, **prediction** (0–3): before grades, the student predicts which test categories their submission will fail and why; scored after grading against what actually failed.

### Process note

Required with every submission. Default: **required but ungraded**; a missing note makes the submission incomplete. Two alternatives the professor may choose instead: (B) fold it into the written component as the 20%; (C) grade it separately and lightly, about 5%. The default keeps the human read to one document.

## 10. Timeline, milestone, appeals

| Week (of 3 / of 5) | What happens |
|---|---|
| 0 | Publish resource, handout, public tests, category names and counts, reference harness install guide. Ledger open. |
| 1 / 1–2 | **Milestone** at the one-third mark: student runs the runner script themselves and the public suite passes. Auto-graded pass/fail, 10%. Forces early install and ends the "it worked in ChatGPT" appeal. |
| 2 / 3–4 | Development. Office hours are about the specification or solution, never about the reference model's behavior. |
| 3 / 5 | Submission. TAs run pre-scan, safety read, runner. Grades out. Hidden tests and seeds released. |
| +1 | Appeals window (§6). |

## 11. Safety and the safety read

Every specification is read by a human before it is executed, to catch malicious instructions planted by the student or injected into the student's workflow from a page the student's own harness fetched. At one TA per 65 students, three controls make that feasible and one of them is the actual safety control:

1. **Sandbox (the real control).** The runner executes every regeneration in a Docker container with outbound network allowed only to the published resource host and the Ollama server, no secrets mounted, a fresh filesystem per run. A line the reader misses cannot do damage. The safety read is therefore an integrity and course-policy check, not the thing standing between a malicious line and the TA's machine.
2. **Length cap.** Specifications are at most 1,500 words including supporting files. A read takes three to five minutes.
3. **Pre-scan.** `tools/prescan.py` flags shell commands, URLs outside the allowlist, credential paths, and instruction-override phrasing ("ignore previous instructions"). The TA reads flagged specifications closely and skims the rest.

Type A solutions are code, and the hidden test runner executes them in the same sandbox.

## 12. Integrity

- **Similarity detection** is the institution's existing checker, named in the handout as `{{SIMILARITY_TOOL}}`. The course submits specifications (Type B) or solutions (Type A) to it and follows the standard misconduct process; the professor handles anything it flags. A specification is text; treat it like code. The framework ships no similarity tool of its own.
- **The twist changes every semester**, so cross-semester copying is moot. Only within-semester sharing matters.
- **Per-student variant parameters** are an option, not the default: each student's resource URL carries a parameter (board size, grid seed, …), and hidden tests are generated per parameter. Copying then requires understanding to adapt. Cost: the runner generates tests per submission and the professor writes a generator instead of fixed cases. Example 4 shows it.

## 13. The professor's workflow

1. **Author.** Pick the type. Write the twist ([checklist](./templates/twist-checklist.md)), the published resource, the interface contract, the public and hidden suites with categories and weights. Fill the [handout template](./templates/handout-type-b.md).
2. **Calibrate.** Write the reference specification. Run the [calibration checklist](./templates/calibration-checklist.md) until it clears every hidden test in at least one run. Set the timeout. Lock the seeds.
3. **Release.** Resource live, ledger open, handout out.
4. **Milestone.** Auto-graded from student-run runner output.
5. **Grade.** TAs follow the [runbook](./templates/ta-runbook.md): pre-scan, safety read, runner, written component, gradebook.
6. **Release hidden tests and seeds.** Appeals window.
7. **Rotate.** Next semester, the [rotation checklist](./templates/rotation-checklist.md): new twist, new nonce, new seeds, new resource URL, new hidden tests, re-verify the reference harness still meets the criteria.

## 14. TA effort at your scale

Two TAs per course, two sections, 30 to 90 students per section, about 1 TA to 65 students.

| Task | Per submission | Per TA (65) |
|---|---|---|
| Pre-scan | seconds, scripted | minutes |
| Safety read | 3–5 min | ~4 hours |
| Regeneration (Type B) | K=3 × ~5–10 min machine time, unattended | 16–32 machine hours, overnight on one box |
| Hidden tests (Type A) | seconds | minutes |
| Written component | ≤10 min | ~11 hours |
| Gradebook | scripted | minutes |

The human total is about 15 hours per TA per project, spread over the grading week. Nothing in the design requires a human to read a transcript.

## 15. Options menu

Things the professor chooses per project, with the framework default first:

| Decision | Default | Alternatives |
|---|---|---|
| Project type | Type B | Type A; both in the same course. **Hybrid, not provided:** a professor who wants it builds a runner mode that grades the solution as Type A and runs the specification as a pass/fail reproducibility gate |
| Project shape | One part | Multi-part with weights, one directory per part, combined by `tools/combine_parts.py` |
| Interface contract | JSON on stdin/stdout | File-argument CLI with fixed stdout format (`prog.py in out depth`) |
| Equivalence policy | `strict` per category | `estimate`, `ab`, `valid` via `check.py` |
| Resource mode | Published resource with the twist | **Research-pointer variant**: the resource points to external documentation plus a twist; snapshot the external page, since it will change |
| Process note | Required, ungraded | Is the written component; separately graded ~5% |
| Ledger strength | Sign with ID + nonce | Add a second instruction the harness must follow from the page (tests instruction-following; also a prompt-injection demonstration, so explain it) |
| Integrity | The institution's similarity checker (`{{SIMILARITY_TOOL}}`) + semester rotation | Per-student variant parameters |
| Regeneration statistic | Best of K=3 | Median (rewards robust specifications); K=5 |
| Graduate bar | Extra category + prediction dimension | Higher threshold on the same tests |
| Pairs | Allowed, both sign | Individual only |
