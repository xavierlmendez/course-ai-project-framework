# The previous project, as actually assigned (Spring 2026)

Source: `Project2.pdf` and `Morris-Variant.pdf` from the professor, plus Xavier's own submission and reproducibility harness (`sillyDrive/school/pythonScriptsSchool/AISpring26`). This corrects the second-hand account in `docs/grill/round-01.md` Q5. Read this before §2 of `framework.md`.

## What was assigned

**Domain.** A Morris variant: a 23-point board (standard nine men's morris has 24), players W and B, 9 pieces each, opening / midgame / endgame (hopping at exactly 3 pieces), mills capture an isolated opponent piece. The handout gives the board, a suggested 23-char string representation, pseudo-code for the move generators, and two static estimation functions.

**Deliverables.** Four parts, eight programs, each submitted as a pair `prog.prompt` + `prog.py`, plus two evidence files:

| Part | Programs | Weight |
|---|---|---|
| I. MINIMAX | `MiniMaxOpening`, `MiniMaxGame` | 45% |
| II. ALPHA-BETA (same estimates, fewer evaluations) | `ABOpening`, `ABGame` | 35% |
| III. Play for Black | `MiniMaxOpeningBlack`, `MiniMaxGameBlack` | 10% |
| IV. Improved static estimation | `MiniMaxOpeningImproved`, `MiniMaxGameImproved` | 10% |
| Evidence | `Examples.txt` (≥2 cases where alpha-beta saves), `MyStaticEstimation.txt` (≥2 differing moves + 1–2 paragraphs) | — |

**Interface contract.** `python prog.py <input_board_file> <output_board_file> <depth>`. Stdout is exactly three lines: `Board Position: <23 chars>`, `Positions evaluated by static estimation: N.`, `MINIMAX estimate: V.`. The output file holds the chosen board.

**AI constraints, verbatim in spirit.** Programs "must be in Python generated by ChatGPT." Students give ChatGPT the handouts, iterate interactively, then ask ChatGPT to produce a prompt that regenerates the same program, and submit that as `prog.prompt`. One prompt per program, one file per program. Students are "not allowed to change the python code directly." Improved static estimation must be described to ChatGPT, not coded by hand. Individual project; prompts and code may not be shared; plagiarism testing on programs.

**Grading checks, verbatim list.**
1. Providing ChatGPT with `prog.prompt` should generate a program functionally identical to `prog.py`.
2. `prog.py` implements the algorithm as described in class.
3. Output has the stated format.
4. `prog.py` is run and graded on correctness.

## What the rubric does not define

These are the gaps the framework closes. None is a criticism of the intent; each is a parameter the rubric leaves open and that decides a grade.

| Gap | Effect |
|---|---|
| **Which model** regenerates from `prog.prompt` | "ChatGPT" spans several models and changes weekly; a prompt tuned on one may fail on another. |
| **Temperature / sampling** | Unspecified, so regeneration is a draw. The complaint recorded in round 1 ("temperature not accounted for") is this line. |
| **How many attempts** | A prompt that works one time in five is either a pass or a fail depending on the grader's patience. |
| **"Functionally identical"** | Undefined. Same board and estimate? Same positions-evaluated count? The count depends on move-generation order, which the handout explicitly allows to differ ("the implementation of the move generator may be different"). Ties between equal-estimate moves are also implementation-dependent. |
| **"Not allowed to change the code directly"** | Unenforceable and unverifiable from the submission. |
| **"Generated by ChatGPT"** | Ties the project to one vendor's account and rate limits; a paid tier gives better models. The paid-model advantage recorded in round 1 is this line. |
| **Positions-evaluated as a graded output** | Correct programs with different but valid child ordering print different counts. A grader comparing to one reference will fail correct work. |

## What Xavier's harness measured

Xavier built a reproducibility harness (`harness/run_repro.py`) that regenerates each program from its prompt via an OpenAI-compatible or Ollama endpoint at temperature 0, then checks syntax, output format, functional equivalence against a reference implementation on 2–3 boards per program, and determinism across repeated runs. Equivalence policies were made explicit in `tests/spec.yaml`: `strict` (board and estimate), `estimate` (estimate only; board may differ on ties), `improved` (against the improved reference), `ab` (estimate equals minimax, node count lower).

Findings, `gpt-4o-mini`, temperature 0:

| Prompt version | Average score | Notes |
|---|---|---|
| v1 (the ChatGPT-produced prompt, as the rubric asks for) | not run at scale | |
| v2 (rewritten with explicit constants and contract) | 60/100 | 4 of 8 programs failed format or functional checks; one was non-deterministic |
| v3 (patched per the failure patterns below) | 100/100 | |
| v4 | 100/100 | |

`PROMPT_TUNING.md` records ten failure patterns of weaker models: invented board topology instead of the given constants; off-by-one in the evaluation counter; markdown fences in output; fail-hard instead of fail-soft alpha-beta; Black variants not swapping colors back; missing the ×1000 in the estimate; wrong terminal-check order; hopping gated on `< 3` instead of `== 3`; improved heuristic omitted; output file not written. Every one is a specification defect that a stronger model papers over and a weaker model exposes.

**What this shows for the framework.**

- The rubric's check 1 *is* a Type B regeneration. The framework does not invent it; it pins the model, temperature, seed, attempt count and equivalence criterion that the rubric left open.
- A specification that reaches 100/100 on a small model is achievable, but only after the specification states constants, contract and algorithm order explicitly. That is the skill Type B grades, and it is why the calibration run against the reference harness must exist.
- Equivalence must be a stated policy per test category (`strict`, `estimate`, `ab`), not the phrase "functionally identical." The framework's per-category `check.py` is that policy.
- Any output that depends on iteration order (a node count) must either be removed from the graded output, or the contract must fix the order. The framework's twist checklist now says so.
- The eight-program shape is a multi-part project; the framework supports it as one project directory per part with part weights (45/35/10/10) combined by `tools/combine_parts.py`.
- The two evidence files map directly onto the written component: `Examples.txt` is a candor/accuracy artifact; `MyStaticEstimation.txt` is the twist-specificity artifact for Part IV.
