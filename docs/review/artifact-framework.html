Course project design · Masters-level CS · prepared 8 September 2026

A course project students solve by directing an AI harness, graded by the course, not by the dice

A reusable framework for projects where students steer an internet-connected agent, no paid subscriptions are needed, TAs can test every submission by script, and two students with the same work get the same grade. Abstracted from course content: the four worked examples cover a board game, A* search, a serialization format, and scheduling, and none of the machinery cares which.

§1The design in one paragraph

A project is a professor-controlled published resource carrying a twist on a well-known problem, plus an interface contract, a public test suite, and a hidden test suite organized in test categories. Students may develop with any tool they like, but the grade comes only from what the reference harness does with their work. The reference harness is a free, local, pinnable model, so every regeneration is reproducible and every submission faces identical conditions. Two project types share all of this and differ only in the graded object. The published resource instructs the harness to sign a ledger, which is how "the harness used the internet" becomes a checkable fact rather than a claim.

Everything on this page is a consequence of that paragraph. The glossary terms above are used exactly throughout; the repo's CONTEXT.md fixes them.

§2Why not grade the prompt

The previous version of this project was a Morris variant on a 23-point board: four parts weighted 45/35/10/10, eight programs, each submitted as a prog.prompt and a prog.py, the Python "generated by ChatGPT" through an interactive session that ended with ChatGPT writing the prompt. The rubric checked four things: the prompt should regenerate a functionally identical program; the program implements the algorithm from class; the output format matches; the program is run and graded on correctness.

That design was already most of this framework. Its first check is a Type B regeneration; its fourth is Type A grading. What it left open is every parameter that decides whether the first check passes:

  1. Which model regenerates from the prompt. "ChatGPT" spans several models and changes weekly.
  2. Temperature and sampling. Unspecified, so a regeneration is a draw.
  3. How many attempts. A prompt that works one time in five is a pass or a fail depending on the grader.
  4. What "functionally identical" means. Same board and estimate? Same count of positions evaluated? The count depends on move-generation order, which the handout explicitly allows to vary, so two correct programs print different numbers.
  5. "Not allowed to change the code directly." Unverifiable from the submission.
  6. "Generated by ChatGPT." Ties the project to one vendor and its paid tiers.

All six share a root cause: the thing that produced the graded output was chosen by the student, not the course. The fix is structural, not a rubric change.

The one move

The course owns the execution. The student owns the specification or the solution; the TAs execute under fixed conditions; the grade comes from that execution and nothing else.

Once the course owns the execution, the model is pinned, temperature is a parameter you set, attempts are a policy you choose, "functionally identical" becomes a stated equivalence policy per test category, and model access stops mattering because the graded model is the same for everyone.

There is evidence this works at the small-model end. A reproducibility harness built for that project regenerated all eight programs from rewritten prompts on gpt-4o-mini at temperature 0. The first rewrite averaged 60/100 with four programs failing. After ten observed failure patterns were folded into the prompts as explicit constraints, every program scored 100/100 and was deterministic. A specification that a small pinned model can execute is achievable, and writing one is exactly the skill Type B grades.

A colleague will ask why the TAs don't simply read and grade the prompt. Because grading a prompt on its merits is exactly the subjective judgment that produces inconsistent grades and appeals. A prompt is a program in a language whose interpreter is a model. You grade programs by running them.

§3Anatomy of a project

Every project, regardless of type or domain, has these parts. The professor authors all of them; the templates and the four examples show the shape.

PartWhat it isWho sees it
Published resourceA page at a URL you control that states the task and the twist, prints the ledger nonce, and instructs the harness to sign the ledger.Everyone
TwistThe deliberate deviation from the canonical problem. Lives in the published resource. Not findable online, under a page, breaks the textbook solution on an identifiable input class.Everyone
Interface contractLanguage, entry point, I/O. Default: Python 3, solve.py, JSON on stdin and stdout. Alternative, as in the previous project: prog.py in out depth with a fixed stdout format. The test runner supports both.Everyone

Hidden test suiteThe full suite in named, weighted categories. Released after grades are out.TAs; students afterward

The published resource is the only structural lever that forces harness use with internet access. A project with no published resource is a traditional project that permits AI, and the framework says so rather than pretending otherwise.

§4Two project types, one set of machinery

Type A

Mastery Project

Understanding of course content is assured by the difficulty of getting a correct solution, not by TA inspection.

  • Submitted: the solution, a process note, a written component.
  • Graded: the solution against the hidden suite, run once. Deterministic.
  • Ledger: a gate. No signed entry, submission incomplete.
  • Regeneration: none. That is the type's whole appeal.
Type B

Specification Project

Skill at specifying a problem precisely enough that a harness solves it.

  • Submitted: a SPEC.md of at most 1,500 words, a process note, a written component. No generated code.
  • Graded: what the reference harness produces from the specification, best of 3 regenerations.
  • Ledger: informational; the TA runner did the fetch.
  • The specification carries the sign instruction. Forgetting it is graded behavior.
Prefer Type A whenPrefer Type B when
The learning goal is the algorithm or data structure itselfThe learning goal is precise specification and verification
TA time is the binding constraintMachine time is available and TA time is not
You want deterministic grading and no regeneration policy to explainYou want the model-access problem removed entirely
Students are expected to read and own the codeStudents are expected to reason about what they told the machine

Both can run in the same course on the same published resource: the graduate section on Type B, the undergraduate section on Type A.

The Hybrid, and how the previous project maps

The previous project submitted both the prompt and the code. In this framework that is a Hybrid Project: the solution is graded as Type A, and the specification is run as a Type B regeneration whose only job is to confirm the solution is reproducible. Two changes from the original rubric: the reproducibility check is a gate, not a score, so a student whose code passes but whose specification cannot reproduce it has submitted code they did not specify; and the rule about not editing code is dropped, because the gate makes it moot. Choose the Hybrid when students must own running code and the specification must still be real. Its cost is that TAs run both paths.

Multi-part projects. Four parts weighted 45/35/10/10 become one project directory per part, each with its own contract, tests and categories, graded separately and combined by weight. Example 01 shows the shape.

§5The reference harness

The framework does not name a harness. It names criteria, and the professor picks an instance each semester, because free tiers change every few months. A reference harness must be:

  1. Free for every student, no card, no paid plan, including practice runs.
  2. Equipped with built-in web fetch, so the published resource works without wiring.
  3. Runnable headless from a script, so TAs batch it.
  4. Temperature-settable, so the schedule in §6 is real.
  5. Model-pinnable, so the model on day 1 is the model on grading day.

Criterion 1 removes every cloud harness whose free tier can reroute or rotate models mid-semester, and removes Claude Code entirely, which has no free path. Criterion 5 is what makes appeals possible.

This year's instance

OpenCode on Ollama, model qwen2.5-coder:14b. OpenCode is the only free open harness surveyed with web fetch and web search built in, headless JSON output, and a pinnable local model. Ollama gives pinned weights plus seed and temperature parameters; per-slot model variants are created from a Modelfile so the pin is harness-independent. 14B is the smallest size to trust with following a one-page resource and satisfying an interface contract. It needs about 9 GB of RAM; the computer lab and the SSH server are the fallback, and the runner takes the Ollama server address as a parameter so a shared server and a laptop produce comparable runs.

Documented alternative: Gemini CLI (Google sign-in, 1,000 requests a day, built-in search and fetch, headless, temperature settable) when a local model is not viable. Its free tier may reroute models, so regenerations are not reproducible; the handout would have to say so.

Students may develop with anything. The handout says: the grade comes from the reference harness, so optimizing for a paid tool is pointless. They install it by the milestone and run the same runner script the TAs use, minus the secret seeds.

§6Regeneration policy for Type B

Best of K, K = 3, at a fixed temperature schedule, identical for every student. Each slot has a fixed seed, secret until grades are released and published afterward with the hidden tests.

Slot 1
0.2
seed s₁ · tag grading-k1
Slot 2
0.6
seed s₂ · tag grading-k2
Slot 3
1.0
seed s₃ · tag grading-k3
  • The grade is the hidden-test score of the best of the three. Best rather than median because the professor chose to give students the best chance; the fixed schedule and seeds keep it fair. Every specification faced the same three conditions.
  • Secret seeds because published seeds invite seed-fitting. Fixed seeds because a regrade or appeal must rerun bit-for-bit.
  • A run that times out (default 20 minutes, calibrated to twice the reference specification's time) or produces a solution that fails to start scores zero for that run. Best-of-K absorbs it.
  • "Reproducible" means: same weights, seed, temperature and wrapper prompt give the same result unless a tool result or the published resource changed. It does not mean deterministic; an agent loop with web access never is. Freeze the resource during grading.

Appeals. One additional regeneration at the middle temperature, granted only if the student shows the specification passes the public suite on the reference harness. Best-of-K makes this rare.

§7Calibration: the one rule not to skip

Gate before release

Your reference specification must pass every hidden test in at least one of the K regenerations on the reference harness. If it cannot, the twist is too hard for the model, not for the students.

Without this rule the grade measures model capability rather than student skill. Fix the twist, the resource wording, or the contract until it passes; do not weaken the tests to fit the model. The calibration run also sets the regeneration timeout and produces the appeals answer key. It costs one afternoon and is the single most important fairness control in the design. The checklist also runs a canonical specification with the twist ignored, which must score visibly low on the twist categories, and an empty one, which must score near zero.

§8The ledger

The published resource contains an instruction like: before writing any code, sign the course ledger with a POST carrying your student ID and the nonce printed on this page. The endpoint:

  • accepts one or two student IDs in the form XXXNNNNNN (three letters, six digits), validated by regex; pairs both sign;
  • records a server timestamp and a run tag (practice, grading-k1..k3, appeal), so TA entries are filterable;
  • requires the nonce from the page, which turns "someone hit the endpoint" into "the harness read the page";
  • is write-only. Student IDs are institutional identifiers and do not belong in a public file;
  • returns a plain error on malformed input so a harness can self-correct.

The framework ships a reference ledger server in about 130 lines of standard-library Python that also serves the resource page. If your site already has a service, port the one route. The ledger cannot distinguish a harness fetch from a student typing curl. Don't try; the handout says so under "What is not graded."

§9Grading

10 milestone35 hidden, other35 hidden, twist20 written

Type A adds the ledger as a gate. The twist categories carry half of the hidden 70 so a canonical solution that ignores the resource cannot collect most of the points from the easy cases.

Equivalence policy

"Functionally identical" is not a test. Every hidden category states what counts as a pass, and its checker implements it.

PolicyPasses whenUse for
strictOutput equals the expected output exactlyDeterministic, order-independent outputs
estimateThe graded value matches; the choice may differ on tiesSearch problems where several moves share the best value
abSame value as the reference algorithm, strictly fewer evaluationsPruning versus exhaustive search
validThe output is a legal solution of the stated cost, checked constructivelyPath-finding, scheduling, anything with multiple optima

An output that depends on iteration order, such as a node count, is either removed from the graded output or the contract fixes the order. Grading it against one reference without fixing the order fails correct work.

Candor is what makes a page hard to fake with a model.

Graduate bar, no extra TA load

Same project. One extra hidden category only graduate submissions are run against (a harder twist variant or a performance bound), added to the same arithmetic so the graduate denominator is larger. Plus the prediction dimension above.

Process note

Required with every submission, ungraded by default; a missing note makes the submission incomplete. Two alternatives the professor may choose: fold it into the written component, or grade it separately at about 5%.

§11Safety and integrity

Every specification is read by a human before it is executed, to catch instructions planted by the student or injected into the student's workflow from a page their own harness fetched. At one TA per 65 students, three controls make that feasible, and one of them is the actual safety control:

  1. Sandbox, the real control. Every run executes in a Docker container with outbound network allowed only to the resource host and the Ollama server, no secrets mounted, a fresh filesystem per run. A line the reader misses cannot do damage, so the safety read is an integrity and policy check.
  2. Length cap. 1,500 words including supporting files. A read takes three to five minutes.
  3. Pre-scan. A script flags shell commands, URLs outside the allowlist, credential paths, and instruction-override phrasing. The TA reads flagged specifications closely and skims the rest.

Integrity. Similarity detection on specifications, treated like code. The twist changes every semester, so cross-semester copying is moot. Per-student variant parameters are an option: each resource URL carries a parameter and hidden tests are generated per parameter, so copying requires understanding to adapt. Example 4 shows what that costs the runner.

§12The professor's workflow

  1. Author. Pick the type. Write the twist against the checklist, the published resource, the contract, the public and hidden suites with categories and weights. Fill the handout template.
  2. Calibrate. Write the reference specification. Run the calibration checklist until it clears every hidden test in at least one run. Set the timeout. Lock the seeds.
  3. Release. Resource live, ledger open, handout out.
  4. Milestone. Auto-graded from student-run runner output.
  5. Grade. TAs follow the runbook: pre-scan, safety read, runner, written component, gradebook.
  6. Release hidden tests and seeds. Appeals window.
  7. Rotate. Next semester: new twist, nonce, seeds, resource URL, hidden tests; re-verify the reference harness still meets the five criteria.

§15Four worked examples

Each ships with a published resource, a reference solution that passes every hidden test, a canonical solution that scores low on the twist categories, public and hidden suites, a filled handout, and a sample student submission.

01 · Type B · multi-part · the previous projectMorris variant, minimax and alpha-beta

The professor's actual Spring 2026 project recast: 23-point board, file-argument CLI, four parts at 45/35/10/10, equivalence policies per category, positions-evaluated made order-safe.

02 · Type A · published resourceA* with a momentum rule

Every fourth step in a straight run is free. Forces a state augmentation and an adjusted heuristic; canonical A* scores 0 on both twist categories.

03 · Type B · research pointerBencode with three changes

The resource points at the BitTorrent BEP 3 page, snapshotted, then changes length prefixes, key order, and booleans.

04 · Type A · variant parametersInterval scheduling with a cooldown

Each student's URL carries a variant; the gap rule derives from it and hidden tests are generated per student.
