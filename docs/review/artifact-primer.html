What the harness does, how to run it, and how to write for it

The course grades your work by running it through an AI harness under fixed conditions. This page explains what that tool is, how to run the same setup yourself, what the grading run looks like step by step, and where to read more. Commands were checked against vendor documentation on 8 September 2026.

§1Chatbot, model, harness: three different things

Model

The network that turns text into text. qwen3:14b is a model. On its own it cannot read a file, run a program, or fetch a page.

Chatbot

A model behind a text box. You paste, it answers, you paste again. Everything that touches your files goes through your hands.

Harness

A program that runs a model in a loop with tools: read and write files, run shell commands, fetch URLs, feed results back until done. OpenCode is one. So are Claude Code, Gemini CLI, Codex CLI and Aider.

This project is graded by a harness, not a chatbot. The harness is what fetches the published resource, signs the ledger, writes the program and runs it. Your specification is instructions to the harness, and the harness decides which tools to use to follow them.

§2What the reference harness is

The course grades with OpenCode running the model named in the project's project.json (the base_model key, this semester qwen3:14b) through Ollama on a machine the TAs control. project.json is the single source of truth: if it disagrees with this page, it wins. Three consequences:

  1. It is free and local. Ollama runs the model on your laptop or on the shared course server. No account, no card.
  2. It is small. A 14-billion-parameter model is far weaker than the frontier chat models you may have used. It follows precise instructions well and guesses badly. A specification that works on a frontier model and fails here has left something unsaid.
  3. It is pinned. The TAs run your specification three times, at temperatures 0.2, 0.6 and 1.0, each with a fixed seed published after grades. Your best run counts.

Develop with whatever you like. The grade comes only from this setup, so anything that only works elsewhere is wasted effort.

§3Install and run it yourself

Ollama and the model

Install Ollama from ollama.com/download (Linux: curl -fsSL https://ollama.com/install.sh | sh; macOS: open the disk image; Windows: the installer). Then:

MODEL=$(python3 -c 'import json;print(json.load(open("project.json"))["base_model"])')   # run from the part directory
ollama pull "$MODEL"      # about 9 GB on disk
ollama run "$MODEL"       # a quick chat to confirm it works; /bye to exit

If your machine cannot run the model. With Ollama on your own machine there is nothing to edit: the ollama_host shipped in project.json is the grading container's view of the model server, and a practice run (no sandbox) substitutes 127.0.0.1 for it automatically. To use the course server instead, add "ollama_host_local" to your own copy of project.json, set to the server URL as your machine reaches it. Leave ollama_host alone, and note that exporting OLLAMA_HOST does not redirect OpenCode: it reads options.baseURL from opencode.json and nothing else.

The course runs the model at a 32,768-token context (num_ctx in project.json), because the agent loop's tool definitions do not fit Ollama's 4,096-token default; at that size the model needs about 15 GB rather than 9, so a 16 GB laptop will swap and the course server is the answer.

Model tags and sizes: ollama.com/library/qwen3. CLI reference: docs.ollama.com/cli.

OpenCode

Install with one of these (opencode.ai/docs), then check with opencode --version:

curl -fsSL https://opencode.ai/install | bash
npm install -g opencode-ai
brew install anomalyco/tap/opencode

The runner writes opencode.json for you, with the model, the base URL and the timeouts already set; the block below is only for running opencode by hand, in the directory holding your work. The shape is from the providers page with the model changed to ours:

{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "ollama": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Ollama (local)",
      "options": { "baseURL": "http://localhost:11434/v1" },
      "models": { "qwen3:14b": { "name": "Qwen3 14B" } }
    }
  },
  "model": "ollama/qwen3:14b",
  "share": "disabled"
}
Keep share off

OpenCode's /share command uploads a session to a public URL. Your specification and the course resource must not end up there. "share": "disabled" prevents it (docs).

Two ways to run

Interactive. Run opencode in your project directory. You get a terminal UI; type a request, watch the tools it calls, ask for changes. Useful commands: /models to confirm the model, /undo to revert the last change, /export to save the conversation as Markdown, /sessions to reopen old ones (TUI docs).

Non-interactive. This is how the TAs run you. The wrapper sentence is identical for every student in a program, and it names two things from project.json: the specification file (spec) and the entry point the harness must produce (entry) — read both there rather than assuming solve.py. Everything else the harness knows comes from your specification and what it fetches.

opencode run -m "ollama/$MODEL" "Read SPEC.md in the current directory and carry out its instructions exactly. The finished program must be a file named solve.py in the current directory. Do not ask questions; make reasonable choices and finish."

Run the course runner for the full grading shape, tests included:

python3 tools/runner.py --project project.json --submission <your dir> --practice

--practice is the only runner command you need. It runs on your machine rather than in the grading sandbox, tags the run practice so it can never be mistaken for a graded one, runs the public suite (you do not have the hidden one), writes seeds.practice.json with three seeds of your own if the secret grading seeds are absent, and creates the pinned per-temperature models if your Ollama has none. Its slot-1 record lands at runs/<your dir>/practice-k1.json and its working directory beside it at runs/<your dir>/practice-k1-work. The milestone is built from those two:

python3 tools/milestone.py record --project project.json \
  --solution runs/<your dir>/practice-k1-work \
  --regeneration runs/<your dir>/practice-k1.json \
  --student-id <your student ID> --out milestone.json

On a Type B project both flags are required and they must belong together: --regeneration is the record of a real practice run (never a dry run, whose record is named *.dry.json), and --solution must be that run's own working directory. A record built from anything else is rejected. milestone.json is the file you submit. (Type A: --solution is simply the directory you are submitting, and there is no --regeneration.)

What the harness can do

OpenCode's built-in tools (docs): read, write, edit, bash, glob, grep, webfetch, websearch, and a few more. In the grading run, bash, edit and webfetch are allowed without prompting, and the network is limited to the published resource and the model server. Your specification can say "fetch this URL", "run this command", "create this file", and the harness will. It cannot reach anything else.

§4The grading run, step by step

  1. A TA reads your SPEC.md, the safety read. It is capped at 1,500 words for this reason.
  2. The runner copies your submission into a fresh sandbox with no secrets and network only to the resource page and the model.
  3. OpenCode starts with the wrapper sentence at slot 1 (temperature 0.2, fixed seed). It reads SPEC.md, fetches the resource, signs the ledger with run tag grading-k1, writes the program.
  4. The hidden test suite runs against what it produced, in a container with no network.
  5. Steps 3 and 4 repeat for slots 2 and 3. Your hidden-test score is the best of the three.
  6. After grades are released you get the hidden tests and the seeds, and you can rerun the exact grading run at home.

A run that exceeds the time limit or produces a program that does not start scores zero for that slot only.

§5Writing a specification a small model can follow

These failure patterns were observed when small models were asked to reproduce last year's programs from prompts. Every one is something the prompt left implicit.

The model…Because the specification…Fix
invented its own board or graph constantsdescribed them in prosePut the exact tables in the spec: "copy verbatim, do not recompute"
counted the wrong thingsaid "count evaluations"Say exactly when the counter increments
wrapped the code in Markdown fencesdid not say the output was a file"Write the file; do not print code"
returned a bound instead of the valuenamed the algorithm and stoppedSpell out the return value and the comparison
got a sign or multiplier wrongwrote a formula in wordsWrite it as an expression
checked conditions in the wrong orderlisted them unorderedNumber them: "in this order"
used < where == was meantsaid "when down to three"Write the comparison
wrote output to the wrong placesaid "output the board"Name the file, the argument index, the exact line format

Three habits that follow:

  • State the interface contract in full, even though the resource has it. The harness reads your spec first.
  • Give one worked example with exact input and exact expected output. Small models anchor on examples.
  • Tell it to check its own work — against the worked example, not against course tools. The harness runs in a directory holding your specification and nothing else: tools/, tests/public/ and the course repository are not there, so "run the public tests" mandates a step that fails during grading and can burn your whole time budget. Say instead: "After writing the program, run it on the worked example from the published resource, compare its output to the expected output character for character, and fix it until they match."
The two lines every specification must contain

Fetch the published resource at its URL. Sign the ledger with your student ID and the nonce from the page — the page shows the exact call:

curl -s -X POST <resource URL>/ledger -d student_id=<XXXNNNNNN>[,<PARTNER>] \
  -d nonce=<nonce from the page> -d run_tag=${RUN_TAG:-practice}

A student ID is three upper-case letters followed by six digits — XXXNNNNNN, for example ABC123456. IDs are upper-cased before they are recorded, so abc123456 is stored as ABC123456; any other shape is rejected.

§6Temperature, seeds, and why "it worked for me" is not an appeal

Temperature scales how random the model's word choices are. At 0.2 the model is nearly repeatable; at 1.0 it wanders. A seed fixes the random draw so the same temperature gives the same output again. Ollama exposes both (Modelfile docs), and the course pins them per slot.

The grading run is reproducible: same model, seed, temperature and wrapper. If your specification passes at home on the same setup and fails in grading, the difference is the seed, and best-of-three exists to absorb that. If it passes on a frontier chat model and fails here, the difference is the model, and that is the thing the project measures.

§7What is and is not graded

Graded: what the reference harness produces from your specification, the written component, the milestone. Not graded: which tool you developed with, how many times you regenerated, whether you fetched the resource by hand, your process note, the harness's transcript.
