Harness Project Brief

Prepared 2026-09-09 by Xavier Mendez · repository course-ai-project-framework · start with framework.md

A reusable way to set a course project in which students direct an AI harness that reads a resource you publish on the web, and to grade the result fairly with two TAs. Each project is a published resource (the rules, on a page you control), a twist (a change to the textbook version that no model knows from training data), an interface contract (how the program is run), and public and hidden tests in weighted categories.

Students submit either code (Type A, graded once) or a specification that the course's reference harness regenerates into code (Type B, best of three runs at fixed temperatures with secret seeds). Every submission signs a write-only ledger on your page, proving the harness fetched the resource. Grades: 10 milestone, 70 hidden tests with the twist categories carrying half, 20 for a written page scored by decision rules. Nothing costs a student money: the reference harness is OpenCode running a local open-weights model through Ollama.

What ships

  • framework.md, the design and your workflow; a glossary; the design-interview transcripts.
  • Templates: handouts for both types, a three-day TA runbook with every command, a rubric with decision rules and worked examples, calibration and rotation checklists, a student primer.
  • Tools in the Python standard library only: pre-scan, resource and ledger server, sandboxed runner with a fixed schedule, grading, multi-part combination, signed milestone records, fan-out from the student layout; 234 unit tests and a rehearsal script.
  • Four worked examples. Example 01 is the Spring 2026 Morris-variant project recast as Type B: all eight programs, each with a reference solution that reproduces the recorded outputs exactly, a canonical untwisted solution that fails the twist categories, and generated test suites.

Three real defects in the harness stack were found and worked around in the runner: OpenCode's five-minute provider timeout, OpenCode reading its project directory from the shell's PWD, and qwen3's thinking mode, which makes the model narrate its plan and end the turn without acting. The slot Modelfiles now carry a patched template that disables thinking.

Decisions that are yours

  1. Should the repository stay public? Example 01 contains complete solutions and hidden tests for the live assignment. Make it private and share access, or move that example's solutions out of the public tree.
  2. Reference model. qwen3:14b with thinking off is the proven instance. Thinking on changes every timing number and has not completed a run.
  3. Grading machine. Timeouts and the grading-day budget are defined as measured on the grading machine. A g5.xlarge on AWS, about one dollar an hour, ran the verification; the calibration run for your reference specification should happen on whichever box will grade.
  4. One written page per project. For a multi-part project the student writes one WRITTEN.md and one PROCESS.md for the whole project, scored once. The sample submission ships that way.
  5. All-twist programs. The handout says "twist categories carry 35 of the 70". A program whose categories are all twist categories makes that false; the tools allow it if declared, but the wording for that case is yours.
  6. Similarity checking. The example handouts name MOSS; the templates leave a placeholder.
  7. Pairs. The tools accept pairs (IDs joined by +); whether the course allows them is your call.
  8. The prior project's description. docs/research/prior-project-spring-2026.md paraphrases the handout and grading checklist. Say if you would rather it were not public.

What happens next

  • You run the calibration gate on your reference specification (templates/calibration-checklist.md): it must clear every hidden test in at least one of the three slots before release.
  • A TA rehearses the runbook with the shipped samples before grading day.
  • Each semester: change the twist and rotate the seeds (templates/rotation-checklist.md).

Getting there took six rounds of correction, and that is the useful part: the gate caught six defects in the reference specifications that no amount of reading would have found, including programs that searched correctly but printed the input board back instead of the move they chose. The four rules that separate a passing specification from a failing one are now in the student primer, because they apply to a student's specification exactly as they do to yours. Decision 2 above is the model choice: the smaller model fits student laptops, the larger one grades six times faster on a 24 GB card.
